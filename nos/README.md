# NOS Service Lambda

## Overview
NOS (Notification & Operations Service) is a serverless service responsible for processing operational alerts and system alarms generated by AWS CloudWatch.  
The service consumes alarm events via SQS, persists alarm history, optionally creates incidents via the Incident Service, and sends notification emails to administrators.

NOS is designed to be resilient to partial failures, supports idempotent alarm processing, and provides observability through structured logging, CloudWatch alarms, and a dead-letter queue.

## Architecture
NOS follows an event-driven, serverless architecture for processing operational alarms.

CloudWatch alarms are published to an SNS topic, which delivers messages to an SQS queue configured for the NOS service.  
The queue acts as a buffer and ensures reliable delivery, batch processing, and failure isolation via a dead-letter queue (DLQ).

The NOS Lambda function is triggered by SQS events and processes alarm messages in batches.  
During execution, the function:
- persists alarm events to MongoDB for history tracking and deduplication,
- invokes the Incident Service Lambda to create incidents for critical alarms,
- sends notification emails using Amazon SES.

Configuration data and sensitive values are retrieved from AWS Secrets Manager.  
Service observability is provided through structured logging, CloudWatch metrics, and technical alarms monitoring Lambda errors and DLQ activity.

Alarm events are produced by external CloudWatch alarms and SNS topics managed outside of the NOS service scope.

## Responsibilities
The NOS service is responsible for:
- processing operational alarm events delivered via SQS,
- validating and normalizing incoming alarm payloads,
- persisting alarm history for auditing and deduplication purposes,
- creating incidents by invoking the Incident Service for critical alarms,
- sending notification emails to administrators,
- handling partial failures and ensuring reliable message processing.

The NOS service is not responsible for:
- generating or managing CloudWatch alarms,
- owning or configuring upstream SNS topics,
- managing the lifecycle or resolution of incidents,
- exposing user-facing APIs.

## Prerequisites
1. **AWS CLI** installed and configured
2. **AWS SAM CLI** installed
3. **Node.js 20+** installed
4. **MongoDB** instance accessible from AWS Lambda
5. **Amazon SES** configured with a verified sender email
6. **Upstream SNS topic** delivering CloudWatch alarm notifications

The NOS service requires several configuration values to operate. In production, these are stored securely in **AWS Secrets Manager**.
Example of this values are in `env.example.json`.
Key variables:
- `MONGODB_URI` – connection string for MongoDB
- `ADMIN_EMAIL` – email address to receive notifications
- `NOS_EMAIL_SOURCE` – verified SES sender email

## Events Supported
The NOS service Lambda processes CloudWatch alarm events delivered via SQS. The main scenarios handled are:

### 1. New Alarm (`ALARM` state)
- Triggered when a CloudWatch alarm enters the `ALARM` state
- Actions performed:
    - Create an incident in the Incident Service Lambda
    - Save the alarm to MongoDB
    - Send a notification email to the admin
    - **Duplicate protection:** if the same alarm for the same timestamp was already processed, no notification is sent
---

### 2. Alarm Resolved (`OK` state)
- Triggered when a CloudWatch alarm resolves
- Actions performed:
    - Update the alarm state in MongoDB
    - Send a resolution notification email
    - Duplicate protection applies here as well
---

### Error Handling

- If an event payload is invalid or cannot be parsed or alarmNam is absent, the Lambda:
    - Logs the error with context (message ID, raw payload)
    - Skips the invalid message and continues processing other events
    - Failing messages are reported to SQS for retry according to batch failure handling

## Logging & Monitoring

The NOS service provides observability through AWS-native logging and monitoring tools.

### Logging

- All Lambda execution logs are written to **CloudWatch Logs**
- The following events are logged:
    - Incoming SQS message metadata (messageId, receiptHandle)
    - Parsed CloudWatch alarm details
    - Duplicate detection results
    - Calls to external services (Incident Service, MongoDB, SES)
    - Errors during payload parsing or processing

Logs can be used to:
- Trace the lifecycle of a single alarm event
- Debug malformed or unexpected payloads
- Investigate retry behavior and DLQ messages

---

### Monitoring & Alarms
The service defines technical alarms to monitor runtime issues:

- **Lambda Errors Alarm**
    - Triggered when the NOS Lambda reports execution errors
    - Helps detect runtime failures, unhandled exceptions, or external service issues

- **Dead Letter Queue (DLQ) Alarm**
    - Triggered when messages appear in the NOS DLQ
    - Indicates messages that failed processing after multiple retries

Both alarms publish notifications to a dedicated SNS topic used for technical alerts.

---

### Failure Visibility

- Messages that cannot be processed successfully after retries are moved to the DLQ
- DLQ messages can be inspected manually to analyze root causes
- Alarm notifications ensure operational issues are detected promptly

## Message Processing & Retry Behavior

- The service is triggered by messages from an Amazon SQS queue.
- Messages are processed in batches of up to 5 records per Lambda invocation.
- Partial batch failure handling is enabled:
    - If processing of a specific message fails, only that message is retried.
    - Successfully processed messages are not retried.
- Each message can be retried up to 3 times.
- After exceeding the retry limit, the message is moved to a Dead Letter Queue (DLQ).


## Failure Handling

- Messages that repeatedly fail processing are moved to a Dead Letter Queue (DLQ).
- The DLQ allows inspection of invalid or problematic alarm payloads without blocking the main queue.
- A CloudWatch alarm is configured to trigger when at least one message appears in the DLQ.
- Both ALARM and OK states of the DLQ alarm are published to a technical SNS topic.
